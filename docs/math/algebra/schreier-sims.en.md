## Introduction

The **Schreier–Sims algorithm** is an algorithm of computational group theory, named after the mathematicians Otto Schreier and Charles Sims. This algorithm can solve, in polynomial time, many problems such as finding the order of a finite permutation group, checking whether a given permutation is contained in a given group, and so on. The Schreier–Sims algorithm was first introduced by Sims in 1970 based on Schreier's lemma. In 1981[^knuth-year], Donald Knuth further improved the running time of the algorithm. Later, a faster randomized version of the algorithm was developed. Computer algebra systems (such as GAP and Magma) usually use a highly optimized Monte Carlo version of this algorithm[^monte-carlo].

???+ info "Notation"
    Following the convention of the computational group theory literature, this article writes group actions as right actions, which means that the composition of permutations proceeds from left to right. The group actions covered in this article can all be regarded as permutation actions, although some algorithms also hold for more general group actions. Correspondingly, the set of a group action is by default $X=\{1,2,\cdots,n\}$, and its elements are called points. The result of a permutation $g$ acting on a point $x$ is denoted $x^g$, and one sometimes also says that the permutation $g$ moves the point $x$ to the point $x^g$. Finally, under the action of a permutation group $G$, the orbit of a point $x$ is denoted $x^G=\{x^g:g\in G\}$, and its stabilizer is denoted $G_x=\{g\in G:x^g=x\}$. The concept of stabilizer can also be generalized to a set $B\subseteq X$, whose stabilizer is defined as $G_B=\bigcap_{x\in B}G_x$.

## Overview

The Schreier–Sims algorithm mainly tries to solve the following problem:

-   Given a set $S$ of some permutations on a set $X$ of size $n$, how can one efficiently store in a computer the permutation group $G=\langle S\rangle$ generated by $S$, and carry out a series of query tasks on this group?

Obviously, such a group $G$ may be very large, far larger than the sizes of the set $X$ and the generating set $S$. For example, the symmetric group $S_n=\langle(123\cdots n),(12)\rangle$ of degree $n$ has size $n!$, but it can be generated by just two permutations. Storing every element of the group is impractical.

Similar to using [Gaussian elimination](../numerical/gauss.md) to build a [linear basis](../linear-algebra/basis.md) of a vector space, the idea of the Schreier–Sims algorithm is to find a "basis" for a finite permutation group $G$:

1.  The input of the algorithm is a generating set $S$ of $G$, containing several permutations;
2.  If the group $G$ is nontrivial, one can always find a point $\beta$ whose position changes under the action of the group $G$, i.e. $|\beta^G|>1$;
3.  Find the orbit $\Delta=\beta^{G}$ of the point $\beta$, and for each point $\delta\in\Delta$ in the orbit, find a permutation $t_{\delta}$ in the group $G$ that can move the point $\beta$ to $\delta$;
4.  Find a generating set $S'$ of the stabilizer $G_{\beta}$ of the point $\beta$;
5.  Recursively call this algorithm on $G'=\langle S'\rangle$, until obtaining the trivial group $\{e\}$.

The rationale of this idea is that the stabilizer $G_{\beta}$ of the point $\beta$ is a subgroup of the group $G$, all of whose (right) cosets form a partition of the group $G$, and these cosets correspond one-to-one with the orbit $\beta^G$ of the point $\beta$; the permutations $t_{\delta}$ found in step 3 are precisely the representatives of these cosets. This set $T$ of coset representatives is called a **transversal** of the stabilizer $G_{\beta}$. In other words, each element $g$ of the group $G$ corresponds to a unique pair of elements $(h,t)\in G_\beta\times T$, and $g=ht$. Therefore, as long as one can find a way to store the subgroup $G_{\beta}$ and the corresponding transversal $T$, one can store the entire group $G$. But the problem of storing the subgroup $G_{\beta}$ has already been solved—one just needs to call the algorithm recursively.

Of course, there are still many details of the algorithm's implementation to be sorted out, which are the main content of this article. But before that, one should first examine the result obtained after calling this algorithm, to see into what kind of structure the algorithm stores the group, and what kind of query problems it can solve. To this end, one should clarify some concepts.

### Stabilizer chain

Suppose the algorithm is called on the group $G=\{S\}$, a total of $k$ times; and at the $i$-th call of the algorithm, the input is the set of permutations $S^{(i-1)}$, the found point is $\beta_i$, the obtained transversal is $T_i$, and the obtained generating set of the stabilizer is $S^{(i)}$. Denoting $G^{(i)}=\langle S^{(i)}\rangle$, the algorithm actually obtains the subgroup chain

$$
G=G^{(0)}> G^{(1)}>\cdots> G^{(k-1)}> G^{(k)}=\{e\}.
$$

Moreover, each subgroup in the chain is a stabilizer

$$
G^{(i)}=G_{\beta_1,\cdots,\beta_i}.
$$

Therefore, the Schreier–Sims algorithm can be regarded as computing precisely such a **stabilizer chain**.

### Base and strong generating set

If a subset $B$ of the set $X$ satisfies $G_B=\{e\}$, then $B$ is called a **base** of the permutation group $G$. Obviously, the above algorithm obtains a base $B=\{\beta_1,\cdots,\beta_k\}$. This means that the result of a permutation $g\in G$ acting on these points uniquely determines this permutation within the group $G$. Moreover, the base output by the algorithm also satisfies the condition

$$
G^{(i-1)}=G_{\beta_1,\cdots,\beta_{i-1}}>G_{\beta_1,\cdots,\beta_{i-1},\beta_i}=G^{(i)}.
$$

That is, each point in the base carries effective information about the elements of the group. Such a base is called **nonredundant**. The algorithm always outputs a nonredundant base. The stabilizer chain corresponding to such a base is strictly decreasing.

At the same time, the union of the generating sets obtained by the algorithm

$$
\bar S=\bigcup_{i=0}^kS_i
$$

is also a generating set of the group $G$, and $\langle\bar S\cap G^{(i)}\rangle = G^{(i)}$ holds. A generating set satisfying this condition is called a **strong generating set** of the group $G$ relative to the base $B$. Therefore, the Schreier–Sims algorithm can also be regarded as computing the **base and strong generating set** (BSGS) of the group $G$. This description and the stabilizer chain description are equivalent, and this article does not distinguish between them.

Of course, the algorithm also obtains a series of orbits $\Delta_i=\beta_{i}^{G^{(i-1)}}$ and the corresponding transversals $T_i$. These orbits are called the **fundamental orbits** of the group $G$. When this article mentions the stabilizer chain, or the base and strong generating set, of the group $G$, it always assumes by default that the corresponding fundamental orbits and transversals have all been computed as well.

### Data structure

This article provides a series of pseudocodes. In the pseudocode, the stabilizer chain (or base and strong generating set) of the group is stored in the data structure $C$:

$$
C=(S,\Delta,T,C').
$$

The data members in this structure are respectively the generating set $S$ of the current group, the fundamental orbit $\Delta$, the corresponding transversal $T$, and the stabilizer $C'$ stored as a nested substructure. Of course, the stabilizer $C'$ is also such a structure. The entire group is actually stored in a layered structure, where each layer describes a group in the stabilizer chain. The innermost layer is an empty structure, representing $G^{(k)}=\{e\}$.

In the pseudocode, the members of this data structure can be accessed respectively via $C.generators$, $C.orbit$, $C.transversal$, and $C.next$. The first element of the orbit, $C.orbit[0]$, is by default the point $\beta$ in the base, and the corresponding coset representative $C.transversal[\beta]$ is by default the identity transformation $e$. Note that although array indices are used here to access the elements of the orbit and transversal, they are not necessarily stored as arrays, but should be understood as providing the methods to access the first element of the orbit and to query the corresponding coset representative given a point in the orbit. The specific implementation details are discussed below.

### Applications

After obtaining the base and strong generating set of a group, one can solve a series of query problems about the group. Among them, the most basic, and the most commonly encountered in competitive programming, are the problems of querying the order of the group and querying whether a given permutation belongs to a given group.

#### Order of the group

If the base and strong generating set of the group $G$ are known, then applying Lagrange's theorem and the orbit-stabilizer theorem shows that the order of the group $G$ can be computed as

$$
|G|=\prod_{i=1}^k[G^{(i-1)}:G^{(i)}]=\prod_{i=1}^k[G^{(i-1)}:G^{(i-1)}_{\beta_i}]=\prod_{i=1}^k|T_i|.
$$

So, one can obtain the order of the group $G$ by simply multiplying together the sizes of all transversals $T_i$ (or equivalently, the lengths of the fundamental orbits $\Delta_i$).

#### Membership testing

Given the base and strong generating set of the group $G$, one can also determine whether a given permutation $h$ belongs to the group $G$. This is called the **membership testing** problem.

This problem can be solved recursively. To determine whether $h\in G^{(i-1)}$, one first finds the representative $t\in T_i$ of the coset of $G^{(i)}$ containing $h$. If it can be found, then letting $h'=ht^{-1}$, we have $h=h't$, and $h\in G^{(i-1)}$ is equivalent to $h'\in G^{(i)}$; the problem is then transformed into determining whether $h'\in G^{(i)}$. If no such $t$ can be found, or one has recursed to $G^{(k)}=\{e\}$ but $h\neq e$, then one can conclude that $h\notin G$. In fact, this process not only determines whether $h\in G$, but in the case $h\in G$ can also express $h$ as a product of a series of coset representatives $t_k\cdots t_2t_1$, where $t_i\in T_i$. For an element of the group $G$, such a representation exists and is unique. This once again proves that the above formula for the order of the group is correct.

Now we write this process as the following pseudocode:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{MembershipTest}(C,h):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for a group }G\textrm{ and a permutation }h.\\
\textbf{Output. }\textrm{Whether }h\in G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{while }C\textrm{ is not empty }\\
2  & \qquad \beta \leftarrow C.orbit[0]\\
3  & \qquad \delta \leftarrow \beta^h\\
4  & \qquad \textbf{if }\delta\in C.orbit\textbf{ then}\\
5  & \qquad \qquad t \leftarrow C.transversal[\delta]\\
6  & \qquad \qquad h \leftarrow ht^{-1}\\
7  & \qquad \textbf{else }\\
8  & \qquad \qquad \textbf{return }\textrm{false}\\
9  & \qquad \textbf{end if}\\
10 & \qquad C \leftarrow C.next\\
11 & \textbf{end while}\\
12 & \textbf{return }h=e
\end{array}
\end{array}
$$

As will be seen below, the membership testing problem is also an important component of the implementation of the Schreier–Sims algorithm discussed in this article.

## Computing orbits, transversals, and stabilizers

To implement the Schreier–Sims algorithm, one must first solve the following subproblem:[^orbit-algo]

-   Given a generating set $S$ of a group $G$ and a point $\beta$, how does one find the orbit $\beta^G$, the corresponding transversal $T$, and a generating set of the stabilizer $G_\beta$?

This is the problem to be solved in this section.

### Storing orbits and transversals

To find the orbit and transversal, one just needs to search directly. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversal}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{ and the transversal }T.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & \textbf{for }\delta\in\Delta\\
4  & \qquad \textbf{for }s\in S\\
5  & \qquad \qquad \gamma \leftarrow \delta^s\\
6  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
7  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
8  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
9  & \qquad \qquad \textbf{end if}\\
10 & \qquad \textbf{end for}\\
11 & \textbf{end for}\\
12 & \textbf{return }\Delta, T
\end{array}
\end{array}
$$

In a concrete implementation, either breadth-first search or depth-first search may be used. The number of states traversed by the search is $|S||T|$, and as long as the orbit and transversal are stored reasonably, the time complexity is entirely acceptable.

Since in the context of permutation groups an orbit is nothing but a set of at most $n$ points, in order to efficiently perform lookup and insertion operations, one can store it using a boolean array or an unordered set. In this way, the time complexity of both operations is $O(1)$, and the overall space usage is $O(n)$. Of course, depending on the implementation of the transversal, one may also need to additionally mark the position of the first element.

The question is what kind of data structure to use to store the corresponding transversal $T$.

#### Direct storage

The simplest method is, of course, to directly store each element $t$ in the transversal $T$. A single permutation is stored in [one-line notation](../permutation.md#单行记号), requiring exactly $n$ space, so the space complexity of storing such a transversal is $O(|T|n)$. The advantage of this is that the time complexity of accessing a single coset representative is $O(1)$, at the cost of an initial time complexity of $O(|T|n)$ to compute these coset representatives.

#### Schreier tree

Another common approach is to implement a tree structure to store the transversal. It is called a **Schreier tree** or **Schreier vector**[^schreier-vector]. It has $\beta$ as its root and the elements $\delta$ of the orbit $\Delta$ as its vertices. Each time a new vertex $\gamma=\delta^s$ is obtained during the search process, an edge is drawn from the old vertex $\delta$ to the new vertex $\gamma$, and the index (or pointer) of the permutation $s$ in the generating set $S$ is recorded on the edge. Because the generating set has already been stored, the additional space complexity of storing the transversal is $O(|T|)$. For the case where the scale of $n$ is very large, this can effectively save space, and the complexity of the initial computation is $O(|T|)$. But the side effect is that each time a coset representative is needed, one needs to traverse the edges on the path from the vertex to the root and recompute the coset representative, so the time complexity highly depends on the depth of the Schreier tree. In the general case, the depth of the tree may reach the level of $O(n)$.

In a concrete implementation, one needs to trade off the time and space complexity of the algorithm according to the actual situation. For the situations that competitive programming may involve, $n$ is usually not large, space is sufficient, and the time complexity often becomes the bottleneck. As will be seen shortly, the most time-consuming step of the Schreier–Sims algorithm happens to require accessing coset representatives many times, so using direct storage is often preferable. But for certain application scenarios, $n$ may be very large and storage space may be more limited, so it may be necessary to use the Schreier tree to store the transversal. For this case, to avoid the Schreier tree becoming too deep, researchers have proposed many methods that can reconstruct a shallow Schreier tree when the tree becomes too deep. Interested readers may consult the references at the end of the article.

In the pseudocode, this article does not distinguish between specific implementations of the transversal, but only assumes that the data structure storing the transversal $T$ implements the operations of accessing and modifying the corresponding coset representative $T[\delta]$ given an orbit element $\delta\in\Delta$.

### Schreier's lemma

After obtaining the orbit $\beta^G$ and the transversal $T$, Schreier's lemma then provides a method for obtaining a generating set of the stabilizer $G_\beta$.

???+ note "Schreier's lemma"
    Let the group $G=\langle S\rangle$ have a subgroup $H\le G$. Let $T$ be a (right) transversal of the subgroup $H$ with $e\in T$[^schreier-lemma-unity], and denote by $\overline g$ the representative $t\in T$ of the coset in which $g\in G$ lies. Then, the set
    
    $$
    U=\{ts(\overline{ts})^{-1}:t\in T,s\in S\}
    $$
    
    is a generating set of the subgroup $H$. Its elements are called the **Schreier generators** of the subgroup $H$.

??? note "Proof"
    First, by the definition of coset representative, $ts(\overline{ts})^{-1}\in H$ holds for all $t\in T,s\in S$, so $\langle U\rangle\subseteq H$.
    
    Conversely, for any $h\in H$, because $S$ is a generating set of $G\ge H$, there must exist a sequence $s_i\in S\cup S^{-1}$ such that
    
    $$
    h=s_1s_2\cdots s_r
    $$
    
    holds. Let $t_1=e$, and recursively define $t_{i+1}=\overline{s_it_i}\in T$; then we have
    
    $$
    \begin{aligned}
    h&=\left(t_1s_1t_2^{-1}\right)\left(t_2s_2t_3^{-1}\right)\cdots(t_rs_rt_{r+1})^{-1}t_{r+1}.
    \end{aligned}
    $$
    
    And for each $i=1,2,\cdots,r$ we have $t_is_it_{i+1}^{-1}=t_is_i(\overline{t_is_i})^{-1}\in U\cup U^{-1}\subseteq H$, so $t_{r+1}\in H$. But $H\cap T=\{e\}$, so $t_{r+1}=e$. This shows that any $h\in H$ can be written as a product of a sequence $u_i=t_is_it_{i+1}^{-1}\in U\cup U^{-1}$, i.e. $U$ generates $H$.

Because the subgroup corresponding to the transversal $T$ is precisely the stabilizer $G_\beta$, after finding the transversal $T$ one can obtain a generating set of the stabilizer $G_\beta$ by combining it with the generating set $S$ of the group $G$.

### Algorithm

With just a slight modification to the above pseudocode, one can obtain a generating set of the corresponding stabilizer while computing the orbit and transversal:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{OrbitTransversalStabilizer}(S,\beta):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G\textrm{ and a point }\beta.\\
\textbf{Output. }\textrm{The orbit }\Delta=\beta^G\textrm{, the transversal }T\textrm{, and a}\\
\qquad\textrm{ generating set }S'\textrm{ for the stabilizer }G_\beta.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \Delta \leftarrow [\beta]\\
2  & T[\beta] \leftarrow e\\
3  & S' \leftarrow [e]\\
4  & \textbf{for }\delta\in\Delta\\
5  & \qquad \textbf{for }s\in S\\
6  & \qquad \qquad \gamma \leftarrow \delta^s\\
7  & \qquad \qquad \textbf{if }\gamma\notin\Delta\textbf{ then}\\
8  & \qquad \qquad \qquad\textrm{append }\gamma\textrm{ to }\Delta\\
9  & \qquad \qquad \qquad T[\gamma] \leftarrow T[\delta]\cdot s\\
10 & \qquad \qquad \textbf{else} \\
11 & \qquad \qquad \qquad \textrm{append }T[\delta]\cdot s\cdot T[\gamma]^{-1}\textrm{ to }S'\\
12 & \qquad \qquad \textbf{end if}\\
13 & \qquad \textbf{end for}\\
14 & \textbf{end for}\\
15 & \textbf{return }\Delta, T, S'
\end{array}
\end{array}
$$

In the pseudocode, for each pair $(\delta,s)$, only when the orbit produces no new element is $t_\delta st_{\delta^s}^{-1}$ a new Schreier generator; otherwise, it is the identity transformation $e$. Therefore, the number of Schreier generators actually produced in the algorithm (including the initial identity transformation) is at most

$$
|S||T|-(|T|-1) = |S|(|T|-1)+1.
$$

For the general case, this upper bound is tight.[^upper-bound] But for the finite groups actually to be handled, this upper bound is quite loose: most of these newly obtained Schreier generators are repetitions of previously obtained generators, or can be composed from previous generators.

Because the basic flow of the Schreier–Sims algorithm can be implemented as recursively calling the above algorithm for computing the orbit and stabilizer, one has in fact already obtained a naive implementation of the Schreier–Sims algorithm at this point. But, without filtering, the growth rate of the number of Schreier generators is exponential: repeatedly applying $O(|S_{i}|)=O(|S_{i-1}||T_i|)$ shows that the size of the generating set of the innermost stabilizer will reach $O(|S||G|)$. This is obviously absurdly inefficient, because the innermost stabilizer is $\{e\}$.

Sims's work provides a method for limiting the growth rate of the number of Schreier generators, which can guarantee that the size of the finally obtained strong generating set $\bar S$ is $O(n^2)$. This makes it possible to compute the base and strong generating set in polynomial time.

## Schreier–Sims algorithm

To solve the above problem, this section discusses an incremental implementation of the Schreier–Sims algorithm, whose obtained strong generating set has size $O(n^2)$.

### Sifting

The core optimization of the Schreier–Sims algorithm over the above naive algorithm is very concise: it requires that before adding any Schreier generator to the generating set of the stabilizer, one first perform **sifting**. So-called sifting is to first determine whether the new Schreier generator already exists in the subgroup generated by the existing generators, and then add only those generators that do not yet exist. To this end, one only needs to use the membership testing algorithm $\textrm{MembershipTest}(C,h)$ from earlier.

But the prerequisite for being able to do this is that, based on the Schreier generators already produced for the current group, one has long since built the stabilizer chain (or base and strong generating set) of the group they generate. This means that each time a new Schreier generator is added to the generating set of the stabilizer, one needs to dynamically maintain the inner stabilizer chain, for use in subsequent sifting. But each time a generator is inserted into the current layer, it may produce multiple Schreier generators, and thus may update the inner structure multiple times; and each update of the inner structure may trigger multiple updates of the even more inner structure.

It seems that the previously mentioned problem of exponential explosion still exists. In fact, it does not. Because sifting is done in advance, only when a generator to be added really triggers an expansion of the structure at some layer does that layer's structure get updated. This shows that the number of updates of a single layer's structure is actually equal to the number of times the group stored at that layer strictly grows. But a group of size $|G|$ has at most a subgroup chain of length $\log|G|$; because Lagrange's theorem guarantees that each increase of the subgroup chain's length by one at least doubles the size of the group. This shows that a single layer's structure is updated at most $\log|G|$ times, so the size of the finally obtained strong generating set $\bar S$ is $|B|\log|G|$.

This estimate can be further improved. Because the group $G$ appearing here is known to be a subgroup of the symmetric group $S_n$ of degree $n$, the length of the subgroup chain of $G$ does not exceed the length of the subgroup chain of $S_n$. It can be proved[^subgroup-chain] that the length of a strictly increasing subgroup chain of $S_n$ does not exceed $3n/2$. This shows that the number of updates of a single layer's structure is in fact $O(n)$. Obviously, the size of the base also does not exceed $n$. Therefore, the size of the finally obtained strong generating set $\bar S$ is $O(n^2)$.

The sifting method mentioned here was proposed by Sims, and is also called the Sims filter. There is also a more complex sifting method proposed by Jerrum, also called the [Jerrum filter](https://groupprops.subwiki.org/w/index.php?title=Jerrum%27s_filter), which can guarantee that the obtained strong generating set has size $O(n)$. Interested readers may study it on their own.

For the sifting process, one small optimization is that, in the implementation of $\textrm{MembershipTest}(C,h)$, one does not output a boolean value, but instead outputs the finally obtained "siftee"[^siftee] $h$ (i.e. replace lines $10$ and $14$ of the pseudocode with $\textbf{return }h$). If the "siftee" $h\neq e$, this means the membership testing failed, and in this case one can directly add the "siftee" $h$ rather than the original $h$ to the current layer. The "siftee" $h$ here has already had several coset-representative factors removed, and thus moves fewer elements, so it reduces the local amount of computation. This optimization has no effect on the overall complexity.

### Procedure

Now one can describe the specific procedure of the Schreier–Sims algorithm: first, initialize an empty structure $C$ for storing the stabilizer chain of the group. Then, add the generators in the generating set $S$ to the structure $C$ one by one; the finally obtained structure $C$ is the stabilizer chain of the group $\langle S\rangle$. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{SchreierSims}(S):\\
\textbf{Input. }\textrm{A generating set }S\textrm{ for a group }G.\\
\textbf{Output. }\textrm{The stabilizer chain }C\textrm{ for the group }G.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & C \leftarrow []\\
2  & \textbf{for }s\in S\\
3  & \qquad C \leftarrow \textrm{Extend}(C,s)\\
4  & \textbf{end for}\\
5  & \textbf{return }C
\end{array}
\end{array}
$$

The core of the algorithm lies in the step of adding a new generator $s$ to the current $C$, i.e. the subroutine $\textrm{Extend}(C,s)$. As stated earlier, both before and after adding the permutation $s$, one needs to ensure that $C$ is a stabilizer chain. Thus, before adding the permutation $s$, one can first do sifting. If it is found that $s$ is not in the existing group, then one **incrementally** computes the orbit, coset representatives, and Schreier generators. The meaning of "incremental" here is that what has already been computed should not be computed again. Only in this way can the correct complexity be guaranteed.

Consider how to transform $\textrm{OrbitTransversalStabilizer}(S,\beta)$ into an incremental version. The state space searched by the algorithm is $\Delta\times S$. After adding the new generator $s$, the state space becomes $\Delta'\times\left(S\cup\{s\}\right)$. The difference between the two is

$$
\left(\Delta\times\{s\}\right)\cup\left((\Delta'\setminus\Delta)\times \left(S\cup\{s\}\right)\right).
$$

This means that when adding the new generator $s$, one first needs to compute the combinations of the new generator $s$ with the old orbit and the corresponding coset representatives; if in this process new orbit elements are also obtained, then one further considers the combinations of these elements with all generators (whether new or old); the process repeats until the orbit no longer lengthens.

The pseudocode for adding a permutation $g$ to the structure $C$ is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10  & \Delta \leftarrow C.orbit \\
11 & \textbf{for }\delta\in\Delta \\
12 & \qquad \gamma \leftarrow \delta^g \\
13 & \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
14 & \qquad \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
15 & \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot g\\
16 & \qquad \textbf{else}\\
17 & \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot g\cdot C.transversal[\gamma]^{-1}\\
18 & \qquad \qquad C.next \leftarrow \textrm{Extend}(C.next, s')\\
19 & \qquad \textbf{end if}\\
20 & \textbf{end for} \\
21 & \textbf{for }\delta\in C.orbit\setminus\Delta \\ 
22 & \qquad \textbf{for }s\in C.generators \\
23 & \qquad \qquad \gamma \leftarrow \delta^s \\
24 & \qquad \qquad \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
25 & \qquad \qquad \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
26 & \qquad \qquad \qquad C.transversal[\gamma] \leftarrow C.transversal[\delta]\cdot s\\
27 & \qquad \qquad \textbf{else}\\
28 & \qquad \qquad \qquad s'\leftarrow C.transversal[\delta]\cdot s\cdot C.transversal[\gamma]^{-1}\\
29 & \qquad \qquad \qquad \textrm{Extend}(C.next, s')\\
30 & \qquad \qquad \textbf{end if}\\
31 & \qquad \textbf{end for}\\
32 & \textbf{end for} \\
33 & \textbf{return }C
\end{array}
\end{array}
$$

This gives the complete Schreier–Sims algorithm.

### Another implementation

The above implementation is already correct, but lines $12$–$19$ and lines $23$–$30$ are somewhat repetitive. Based on this, Knuth proposed a recursive implementation in his paper, which is more concise. His approach is to regard this repetitive part as an update of the transversal (and the orbit). Each update of the transversal must be combined with all generators, and depending on whether a new coset representative is produced, one decides whether to recursively call itself or to call the procedure for adding a generator. The pseudocode is as follows:

$$
\begin{array}{l}
\textbf{Algorithm }\textrm{Extend}(C,g):\\
\textbf{Input. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\textrm{ and a}\\
\qquad \textrm{permutation }g.\\
\textbf{Output. }\textrm{A stabilizer chain }C\textrm{ for the group generated by }S\cup\{g\}.\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \textbf{if }\textrm{MembershipTest}(C,g)\textrm{ is passed}\textbf{ then}\\
2  & \qquad \textbf{return }C\\
3  & \textbf{end if}\\
4  & \textbf{if }C\textrm{ is empty}\textbf{ then}\\
5  & \qquad \beta \leftarrow \textrm{an element moved by }g\\
6  & \qquad C.orbit[0] \leftarrow \beta \\
7  & \qquad C.transversal[\beta] \leftarrow e\\
8  & \textbf{end if}\\
9  & \textrm{append }g\textrm{ to }C.generators\\
10 & \textbf{for }t\in C.transversal\\
11 & \qquad \textrm{ExtendTranserversal}(C,t\cdot g)\\
12 & \textbf{end for}\\
13 & \textbf{return }C
\end{array}\\
\\
\textbf{Sub-Algorithm }\textrm{ExtendTranserversal}(C,t):\\
\textbf{Method.}\\
\begin{array}{ll}
1  & \beta \leftarrow C.orbit[0]\\
2  & \gamma \leftarrow \beta^t\\
3  & \textbf{if }\gamma\notin C.orbit\textbf{ then}\\
4  & \qquad \textrm{append }\gamma\textrm{ to }C.orbit\\
5  & \qquad C.transversal[\gamma] \leftarrow t\\
6  & \qquad \textbf{for }s\in C.generators\\
7  & \qquad \qquad \textrm{ExtendTranserversal}(C,t\cdot s)\\
8  & \qquad \textbf{end for}\\
9  & \textbf{else}\\
10 & \qquad s' \leftarrow t\cdot C.transversal[\gamma]^{-1}\\
11 & \qquad \textrm{Extend}(C.next,s')\\
12 & \textbf{end if}
\end{array}
\end{array}
$$

Comparing the pseudocode here with that of the previous section, one can see that it is correct. Moreover, the two have no difference in complexity.

### Complexity

To analyze the complexity of the Schreier–Sims algorithm, some notation is needed. Let the length of a permutation be $n$, and the size of the generating set $|S|$ be $m$. Denote the length of the obtained (nonredundant) base by $|B|$. Moreover, in the finally obtained stabilizer $G_i$ at the $i$-th layer from the outside in, denote the number of generators by $|S_{i-1}|$ and the size of the transversal (or the length of the orbit) by $|T_i|$. Below we analyze the time complexity required by the above incremental implementation of the Schreier–Sims algorithm. The algorithm is mainly divided into two parts: sifting, and the computation of orbits, transversals, and Schreier generators.

Both the initially input generators and the Schreier generators obtained in the algorithm need to be sifted, so the total number of times the sifting process is executed is $O(\sum_{i=1}^{|B|}|S_{i-1}||T_i|+|S|)$. A single sifting requires computing the permutation product with $O(|B|)$ coset representatives. Let the time to compute the product with a single coset representative be $\tau$. When directly storing the coset representatives, $\tau\in O(n)$; when storing the coset representatives with a Schreier tree, $\tau\in O(n^2)$. The total time complexity of executing the sifting process is $O(\tau|B|\sum_{i=1}^{|B|}|S_{i-1}||T_i|+\tau|B||S|)$.

For the computation of information such as orbits, because it is an incremental implementation, each pair $(\delta,s)\in\Delta_i\times S_{i-1}$ in the state space is computed at most once. For the computation of the orbit and transversal, depending on the storage method, the time complexity of a single computation of a coset representative may be $O(n)$ or $O(1)$. But in any case, this does not exceed the complexity of computing a Schreier generator. With direct storage, it is $O(n)$; with a Schreier tree, it is $O(n^2)$. Comparing with the total time complexity of the sifting process, one finds that the time complexity of computing this information does not exceed the time complexity required by sifting. So, the time complexity of the Schreier–Sims algorithm is precisely the $O(\tau|B|\sum_{i=1}^{|B|}|S_{i-1}||T_i|+\tau|B||S|)$ obtained in the previous paragraph.

As for the space complexity, the data structure finally obtained by the algorithm stores $O(\sum_{i=1}^{|B|}|S_{i-1}|)$ generators and $O(\sum_{i=1}^{|B|}|T_i|)$ coset representatives. If direct storage is used, both generators and coset representatives require $O(n)$ space; if a Schreier tree is used, generators require $O(n)$ space, while coset representatives require only $O(1)$ space.

It has been explained earlier that the length of a strictly increasing subgroup chain in the symmetric group of degree $n$ is $O(n)$, which applies to both $|B|$ and $|S_i|$. Therefore, the Schreier–Sims algorithm implemented using the direct-storage transversal has time complexity $O(n^5+mn^2)$ and space complexity $O(n^3)$. Of course, for the case $\log|G|\in O(n)$, a better estimate is the time complexity[^knuth-complexity] $O(n^2\log^3|G|+mn\log|G|)$ and the space complexity $O(n^2\log|G|)$. For the case of a random generating set, actual testing finds that the complexity of the algorithm is significantly lower than $\Theta(n^5)$, being roughly $\Theta(n^4)$.

Although, compared with direct storage, using a Schreier tree introduces an extra exponent of $n$ into the time complexity, for the case where $n$ is very large but the group itself is far smaller than the symmetric group of degree $n$, its space complexity is $O(n\log^2|G|)$, far smaller than the $O(n^2\log|G|)$ of direct storage. But in competitive programming, it is difficult to encounter such a situation where storage with a Schreier tree is preferable.

### Reference implementation

Here we provide a reference implementation of the Schreier–Sims algorithm. Because the scale of $n$ is relatively small, the implementation directly specifies the base $B=\{n,n-1,\cdots,1\}$ rather than choosing it through the algorithm. The advantage of this is that the permutations in the group at the $k$-th layer from the inside out (not counting the empty structure) change only the first $k$ elements, which facilitates subsequent computation. Another optimization in the code is that, when storing a coset representative, what is actually stored is its inverse permutation, which simplifies the operations on permutations.
